# Phase 0 Research: Ship Combat System

**Feature**: `specs/003-ship-combat-system/spec.md` · **Date**: 2026-10-14

No Technical Context unknowns remained (stack TypeScript + Excalibur + Vite + Vitest, sim/scene split, seedable `Rng` adapter, and `board.json` tuning are established by `001-grid-ship-spawn` / `002-agility-based-movement`). The entries below resolve this feature's new design decisions. Clarification answers from 2026-10-14 (d20 1–20 HP base; End Turn / Skip Attack control; one optional move + one optional attack in any order; turn continues after attack while move remains) are treated as decided inputs.

## R-01: Combat tuning lives in `board.json` under a `combat` section; stat→modifier table shared

- **Decision**: Add an additive `combat` section to `src/config/board.json`: `strength.rollRange [8,20]`, `constitution.rollRange [8,20]`, one shared `statTable` (the exact 001/002 agility bands: 8–9 → −1, 10–11 → 0, 12–13 → 1, 14–15 → 2, 16–17 → 3, 18–19 → 4, 20 → 5), `armorClass: 12`, `hitPoints: { die: 20, perModifierBonus: 2, minStart: 1 }`, `attack: { die: 20, hitMeetsAC: true }`, `damage: { die: 8, minDamage: 1 }`, plus `torpedo` visual parameters (blink rate, travel speed, explosion descriptor, near-miss offset). `combat.ts` reads all of it; no combat number is hard-coded in logic. The existing `agility` section stays untouched so 001/002 configs validate unchanged; the shared table is referenced (not duplicated) so future retunes stay single-source.
- **Rationale**: Satisfies Principle IV — retuning AC, dice, or the table is a data edit with no logic rewrite, and the spec's exact mapping (including the irregular single-value `20 → 5` row) stays reviewable as data, consistent with R-01 of 002.
- **Alternatives considered**: Formula-based modifier (`floor((stat−10)/2)` — matches most rows but obscures the authored table and breaks silently on retune — rejected); constants in `combat.ts` (violates Principle IV — rejected); separate strength/constitution tables (spec mandates the shared mapping — rejected as spec-violating).

## R-02: RNG draw order — spawn, agility, then combat, appended per ship

- **Decision**: Setup consumes the seeded stream in pinned order preserving 001/002: (1) spawn ship-1, (2) spawn ship-2, (3) agility ship-1, (4) agility ship-2 (unchanged), then (5) strength ship-1, (6) strength ship-2, (7) constitution ship-1, (8) constitution ship-2, (9) HP-base d20 ship-1, (10) HP-base d20 ship-2. In-battle rolls append in play order: each attack consumes exactly one d20; a hit consumes exactly one further d8 (miss consumes none). Same `(configVersion, seed)` + action sequence reproduces identical stats, rolls, HP, and winner (FR-019, SC-007).
- **Rationale**: Satisfies Principle I and protects the 001/002 investment — earlier draws keep their stream positions, so existing seed→position/agility expectations are preserved; combat draws are appended, not interleaved. Fixed per-ship and per-attack ordering removes the last nondeterminism source.
- **Alternatives considered**: Combat rolls before agility/spawn (shifts the whole stream, invalidating 001/002 seed expectations — rejected); separate RNG streams for combat (two seeds to record/replay — rejected, same argument as 002 R-02); `Math.random` anywhere (not seedable — rejected).

## R-03: Combat resolution as a pure function in `combat.ts`

- **Decision**: New pure, engine-free `combat.ts` exposes: `modifierForStat(stat)` (shared-table lookup, throws on zero/multiple band matches — same strictness as `agility.ts`), `rollShipCombatStats(config, shipId, rng)` (strength + constitution + modifiers), `computeHitPoints(config, constitutionModifier, rng)` (d20 1–20 + mod×2, floor `minStart` 1), `resolveAttack(config, attackerStrMod, defenderAC, rng)` returning `{ attackRoll, total, hit, damageRoll?, damage? }` — exactly one d20 always, exactly one d8 iff hit, damage floored at `minDamage` 1. HP application (`currentHP − damage`, clamp ≥ 0) and win detection (`HP ≤ 0 → attacker wins immediately`) live in the turn/battle reducer consuming this result, keeping `combat.ts` side-effect-free.
- **Rationale**: Every rule (mapping edges −1/0, HP formula + floors, ≥AC hit, miss-no-damage, damage minimum, clamp, win-on-0) becomes a Node-runnable fail-first unit test with stub RNG (Principle III); the scene never duplicates combat math (Principle II).
- **Alternatives considered**: Combat logic inside `battle-scene.ts` (needs browser harness per roll — rejected); damage rolled on misses (violates FR-011, wastes stream determinism — rejected); negative/zero damage (spec edge case demands min 1 so a hit always matters — rejected).

## R-04: Two-action turn as a pure reducer extension in `turn.ts`

- **Decision**: Extend `TurnState` to `{ activeShipId, turnNumber, moveUsed: boolean, attackUsed: boolean, legalSet, over: { winner } | null }`. New reducer operations (all pure, immutable): `skipMove(state)`, `skipAttack(state)` / `endTurnEarly(state)` (mark used, no rolls, no movement), `dispatchAttack(state, targetShipId, rng)` (only when `!attackUsed && target === foe && !over`; consumes rolls via R-03, marks `attackUsed`, applies HP, sets `over` on kill), `resolveMove` (existing, now marks `moveUsed` instead of ending the turn). Turn advances (`activeShipId` flips, `turnNumber + 1`, flags reset, fresh `legalSet`) only when `moveUsed && attackUsed`, on `endTurnEarly`, or never after `over` (terminal — all further dispatches rejected). Selecting empty squares / own ship with attack unused is a no-op that consumes nothing (FR-009). Rapid double-selection is safe: the first accepted attack flips `attackUsed`, the second resolves against used state and is ignored.
- **Rationale**: Keeps turn alternation, any-order actions, at-most-once enforcement, and win-terminality in tested pure code (Principles I + III); the scene stays a thin click→dispatch→render adapter, mirroring 002 R-04. Stay-in-place via Skip Movement control or current-square confirm both consume `moveUsed` with no relocation.
- **Alternatives considered**: Move-must-precede-attack fixed order (contradicts clarification 3 — rejected); attack ending the turn (contradicts clarification 4 — rejected); mutable turn singleton (harder to test sequences/replays — rejected, same as 002 R-04).

## R-05: Click routing — enemy-ship selection launches torpedo, everything else is movement/skip

- **Decision**: Scene left-click maps to a board cell: if the cell holds the **enemy** ship and `!attackUsed && !over`, dispatch `dispatchAttack` (launch torpedo regardless of grid distance — unlimited range per assumption); else if the cell is in `legalSet` and `!moveUsed`, dispatch `resolveMove`; else ignore with no state change and no roll consumed. Skip Movement and End Turn / Skip Attack are on-screen controls (real clickable UI, keyboard-accessible) active only while their action is unused. After `over`, all clicks are ignored.
- **Rationale**: Implements FR-007/FR-009/FR-020 with zero ambiguity; unlimited range avoids inventing a range/LOS system the spec excludes (Principle V); no-op clicks preserve RNG stream determinism.
- **Alternatives considered**: Range-limited attacks (spec assumption says unlimited — rejected as speculative); click-to-select-then-confirm two-step (spec says attack is made by clicking the enemy ship — single action — rejected); modal dialogs for skips (heavier than inline controls — rejected).

## R-06: Torpedo animation — one blinking-star projectile, hit vs. near-miss paths

- **Decision**: Presentation-only animation in `battle-scene.ts` using existing Excalibur primitives (Actor + procedural star graphic + blink timer + linear path action): on hit, the star travels attacker-center → defender-center then a contact explosion effect plays and the HP reduction renders with the outcome text; on miss, the star travels attacker-center → near-miss waypoint (defender-center offset perpendicular by the data-driven `torpedo.nearMissOffset`, e.g. ~0.75 tile) → continues along the same heading off-grid and despawns, with no explosion on the ship. Animation never changes the pre-rolled outcome; the outcome text renders in connection with (not after hidden delay of) the animation, and input during flight is queued/ignored so no second attack dispatches. Torpedo speed/blink/offset come from `board.json` `torpedo` tuning.
- **Rationale**: Implements FR-015/FR-016 + SC-005 with the simplest legible treatment (Principle V); path + explosion + text keeps hit/miss non-color-only (Principle II + accessibility baseline); data-driven visuals keep tuning out of logic (Principle IV).
- **Alternatives considered**: Particle-system torpedo with trails (disproportionate for one projectile — rejected); same path for hit and miss differing only in color (violates non-color-only baseline — rejected); blocking the sim on animation completion (mixes presentation timing into deterministic rules — rejected; the reducer resolves instantly, the scene animates the already-decided outcome).

## R-07: HUD disclosure — stats, HP, actions, rolls

- **Decision**: Persistent on-screen panel (status line + per-ship stat block, text — never color-only): each ship shows `STR x (±m) · CON y (±m) · HP cur · AC 12`; turn line shows `Turn n — Player X (ship-i) to act · Move: available/used · Attack: available/used`; on each attack, an outcome line/log shows `attack roll R + mod = total vs AC 12 → HIT/MISS` plus on hit `damage roll D + mod = dmg → defender HP a → b`. Win line declares `Player X wins` and disables further input.
- **Rationale**: Implements FR-008/FR-017/FR-018 + SC-006 (explainable within 10 s); text disclosure keeps the game playable without interpreting animation (Principle II).
- **Alternatives considered**: Animation-only feedback (fails SC-006 and accessibility — rejected); full combat-log window with history/scroll (speculative chrome for two ships — rejected; a last-outcome line + optional rolling 3-line log suffices per Principle V).

## R-08: Test strategy (automated vs. manual)

- **Decision**: Vitest suites in `tests/unit/`: `combat.test.ts` (every table band + boundaries 8/9/10/11/12/20 incl. −1/0 edges; HP formula example base 10 + mod 2 → 14; HP floor 1 on negative constitution; fixed AC 12; ≥AC hits / <AC misses incl. 10+2=12 hit and 9+1=10 miss; miss consumes no damage roll and changes no HP; damage floor 1; HP clamp at 0 and immediate win with attacker declared; no further actions post-win; draw-order determinism incl. attack-then-damage sequencing; same-seed replay equality); `turn.test.ts` additions (attack-before-move allowed; second move/attack rejected; skip controls consume without state change or rolls; both-used/early-end passes turn; empty/own-ship selection no-ops; double-selection single-launch); `validation`/`board-config` additions (combat config shape, gappy/overlapping table rejection); `spawn`/`agility` regressions (existing seeds unchanged). Manual browser checklist in `quickstart.md` covers HUD legibility, skip controls, hit/miss animation paths, and the 10-second explainability check.
- **Rationale**: Every rule, transition, and seeded edge case gets a fail-first automated test (non-negotiable Principle III); rendering/feel stays manual per constitution allowance. Suite-per-module keeps failures local.
- **Alternatives considered**: Browser-driven animation tests (flaky, disproportionate — rejected, same as 002 R-07); single combined test file (obscures which rule regressed — rejected).
